# Archora — Benchmarks

This file is the public scorecard for Archora analyzer accuracy.
It is updated by `scripts/run-benchmarks.ts` and committed on each release.

> Why this exists: insights are only useful if you can trust them. We treat
> precision and recall as a first-class quality signal, with the same weight
> as test coverage or build success. The table below is the truth, including
> when it's bad.

## How metrics are computed

For each reference project we maintain a hand-written `expected.json` that
classifies the analyzer's outputs:

- **truePositives** — insights the analyzer should produce, and they are real.
- **falsePositives** — insights the analyzer currently produces but they are wrong.
- **missed** — issues we know exist in the project but the analyzer doesn't (yet) detect.

An emitted insight matches an annotation if their `kind` is the same and at
least one module is shared between them.

| Term | Definition |
|---|---|
| TP | matched a `truePositives` annotation |
| FP | matched a `falsePositives` annotation |
| FN | annotation in `missed` that no insight matched |
| Unverified | analyzer-emitted insight that matched neither TP nor FP — counts as FP for the purposes of precision (incentive: annotate everything) |
| Precision | `TP / (TP + FP + Unverified)` |
| Recall | `TP / (TP + FN)` |
| F1 | harmonic mean of precision and recall |

Aggregate metrics sum TP/FP/FN/Unverified across all projects, then recompute.

## Targets

| Metric | v1.0 release gate |
|---|---|
| Aggregate precision | ≥ 90% |
| Aggregate recall | ≥ 80% |
| Aggregate F1 | ≥ 85% |
| Per-project F1 | ≥ 70% (no project is allowed to be much worse than aggregate) |

These thresholds are the project-wide gate; the per-fixture rationale
(why each annotation is or isn't a real positive) lives next to each
`expected.json` in the fixture directory.

## Running

```bash
npm run bench                                     # all projects
npm run bench -- vue-spa                          # filter by name
npm run bench -- --update-md                      # rewrite the table below
npm run bench -- --json                           # full JSON to stdout
npm run bench -- --threshold-precision=0.9        # CI gate
```

A timestamped JSON report is also written to `dist/benchmarks/` for diffing.

## Cross-tool differential validation

The reference-corpus F1 above measures the analyzer against annotations we
write ourselves — useful for catching regressions, but not independent
evidence of accuracy. To validate against code we did not tune for, we run
cycle detection against [`madge`](https://github.com/pahen/madge) as an
independent oracle on third-party TypeScript repositories
(`scripts/accuracy-diff.ts`, repos fetched on demand, not committed).

We compare three "files in a cycle" sets per repo: Archora, `madge` with
`skipTypeImports: true` (a runtime-leaning oracle — TypeScript erases `import
type`, so it forms no runtime cycle), and `madge` default. `onlyArchora` is a
cycle Archora reports and madge-fair denies (a false positive); `onlyMadge` is
the reverse (Archora reports fewer).

| repo | Archora | madge-fair | onlyArchora (FP) | onlyMadge | type-only FPs madge-default emits, Archora avoids |
|---|--:|--:|--:|--:|--:|
| zustand | 0 | 0 | 0 | 0 | 0 |
| jotai | 0 | 0 | 0 | 0 | 4 |
| redux | 0 | 0 | 0 | 0 | 0 |
| pinia | **0** | 2 | 0 | 2 | 0 |
| mobx | 52 | 52 | 0 | 0 | 0 |
| react-query | 0 | 0 | 0 | 0 | 15 |
| xstate | **18** | 26 | 0 | 8 | 7 |

Three results:

1. **Zero false positives** across every repo — Archora never invents a cycle
   the oracle denies (`onlyArchora = 0`), including the large graphs (mobx 52,
   xstate). This is the property that matters for trust in CI.

2. **Archora is stricter than madge-fair where it should be.** On pinia and
   xstate, Archora reports *fewer* cycles than even the fair oracle (`onlyMadge`
   of 2 and 8). madge-fair keys on syntax: it skips `import type` but cannot see
   a *value-syntax* import used only in type positions, which the compiler still
   erases. Archora does. Spot-checked on pinia: the two cycles madge-fair reports
   are `types.ts → rootStore.ts` (`import { Pinia }`, an interface) and the
   reverse (eight type names from `./types`) — pure type imports, no runtime
   edge. The accuracy gate surfaces this `onlyMadge` direction as
   "stricter-than-madge" for review rather than treating it as a miss.

3. Archora also avoids **26 type-only false-positive cycles** that `madge`
   reports in its default mode (last column), because it tracks `import type` as
   a distinct edge kind.

Net: on this curated corpus, less noise than madge in two independent ways
(default-mode type imports, and value-syntax type-only imports the fair oracle
still misses), with no false positives, measured on code we did not tune for.

### Extended corpus (coverage, not a clean sweep)

The harness also runs six framework/app repos (vue-core, vue-router,
react-router, excalidraw, vitepress, tanstack-router) so the corpus is not just
flat libraries. These are deliberately **not** treated as gate oracles, and the
results are not all green — reported honestly:

- react-router (5 = 5) and tanstack-router (0 = 0) agree with madge-fair.
- vue-router and vitepress: madge crashes on the monorepo, so no comparison.
- **vue-core and excalidraw show `onlyArchora` cycle counts (12 and 19) that we
  did not confirm.** Here is the nuance: on the file set both tools analyze, the
  *resolved edge graphs are identical* (vue-core 318 = 318; excalidraw differs by
  one edge). So Archora's import resolution is not inventing edges. The cyclic-
  file totals still diverge because the two tools' reachable file *universes*
  differ in these project-reference monorepos (Archora's cycle count equals
  madge's *default* mode on vue-core, not its fair mode). That is an oracle
  reliability problem, not a demonstrated Archora false positive — but neither is
  it a win, so the gate marks it **oracle-divergence (WARN)** and never hard-fails
  on it. Confirming each by hand is open follow-up.

The edge-resolution differential (import resolution vs madge's graph, restricted
to the shared file set) matches exactly on zustand/jotai/redux/pinia/mobx/
react-query/vue-core; xstate and excalidraw differ by a single edge. These are
warnings, not gate failures — the shared-file-set restriction (Archora skips
test-like dirs, madge does not) makes them informative but not airtight. _Corpus
note: a repo whose source layout the harness cannot locate (zod this run) is
dropped from conclusions rather than counted as a zero._

### Edge recall

Quantified, the differential gives **edge recall** = `(madge − onlyMadge) / madge`
— the share of madge-fair's resolved edges Archora also caught, on the shared file
set. Latest run: **100.0% aggregate** (2251 edges, 0 missed) across the eleven
repos the harness can analyze (zod excluded — Archora resolved 0 edges, a
source-location failure, not a recall miss; vue-router and vitepress excluded —
madge crashes on the monorepo). This is a **lower bound** on true completeness:
madge is blind to `React.lazy` / `next/dynamic` and Vue/Nuxt auto-import edges,
which Archora resolves — so 100% vs madge means everything madge sees, plus the
dynamic edges it misses. The number lives in the edges table of
`accuracy-diff-result.md`.

The gate (`npm run accuracy:gate`) hard-fails only on an `onlyArchora` cycle in a
**trusted-oracle** repo (the flat libraries above); complex monorepos are
coverage-only WARN. Current verdict: PASS — 0 trusted false positives, 2
stricter-than-madge (pinia, xstate), 2 oracle-divergence WARN (vue-core,
excalidraw).

Reproduce: `npm run accuracy:diff` (writes
`docs/superpowers/audits/accuracy-diff-result.{json,md}`). The release gate
`npm run accuracy:gate` fails only on a cycle false positive and is safe to run
offline (every repo skips, gate passes).

## Adding a reference project

1. Create `fixtures/reference/<project>/`. Either:
   - copy a synthetic project (small, committed), or
   - add a `clone.sh` that clones a real OSS project at a pinned commit into
     the same directory (gitignored).
2. Run `npm run bench -- <project>` to see what the analyzer currently emits.
3. Walk the output and write `expected.json`:
   - For each emitted insight: classify as `truePositives` or `falsePositives`.
   - Add `missed` entries for issues you know are real but the analyzer didn't find.
4. Re-run with `--update-md`. Commit both the project folder and the new row
   in the table above.

## Annotation schema

```json
{
  "project": "string",
  "description": "string",
  "rev": "string (git sha or 'local-fixture')",
  "expected": {
    "truePositives": [
      { "kind": "isolated-cluster", "modules": ["src/foo.ts"], "note": "..." }
    ],
    "falsePositives": [
      { "kind": "unused-utility", "modules": ["src/utils/loader.ts"], "note": "..." }
    ],
    "missed": [
      { "kind": "cycle-break-candidate", "modules": ["src/a.ts", "src/b.ts"], "note": "..." }
    ]
  }
}
```

`kind` is one of `split-god-module`, `unused-utility`, `cycle-break-candidate`,
`misplaced-by-layer`, `isolated-cluster` (see `core/analyzer/types.ts`).
